# Security Policy — VetAssistant

Версия **1.1.0** — текущий production-релиз VetAssistant со сменой пароля,
оптимизацией памяти и базовой защитой сервера. Мы серьёзно относимся к
безопасности данных владельцев животных, учётных записей и инфраструктуры.
Этот документ описывает политику, порядок сообщения об уязвимостях и
обязательный чеклист production-деплоя.

## Поддерживаемые версии

| Версия | Поддержка | Примечание |
|---|---|---|
| `1.x` | ✅ Активная | Security-обновления и исправления |
| `< 1.0.0` | ❌ Не поддерживается | Прототипы и preview-релизы |

## Как сообщить об уязвимости

**Пожалуйста, не создавайте публичный issue с деталями уязвимости.**

Предпочтительный способ — приватный GitHub Security Advisory:

1. Откройте вкладку **Security** репозитория
   [iilmchat/ai_VetAssistant](https://github.com/iilmchat/ai_VetAssistant/security).
2. Нажмите **Report a vulnerability**.
3. Опишите проблему, шаги воспроизведения, влияние и, если возможно,
   предложите исправление.

Если приватный отчёт недоступен, создайте публичный issue **без
технических деталей** с заголовком `Security contact request` — мейнтейнер
свяжется с вами и предоставит приватный канал.

В отчёте желательно указать:

- затронутую версию/коммит и компонент (`api`, `frontend`, `bot`, deploy);
- тип уязвимости (например, обход авторизации, утечка данных, XSS,
  SSRF, RCE, утечка секретов);
- шаги воспроизведения и ожидаемое/фактическое поведение;
- оценку влияния и известные ограничения;
- контакт для связи.

### Что мы обещаем

- Подтвердим получение отчёта в течение **72 часов**.
- Проведём первичную оценку в течение **7 дней**.
- Для критичных уязвимостей выпустим исправление в течение **30 дней**
  (по возможности быстрее).
- Уведомим о сроках и согласуем публичное раскрытие после выпуска фикса.
- Укажем автора отчёта в release notes, если он этого хочет.

Мы не платим вознаграждение за уязвимости (bug bounty), но ценим каждый
ответственный отчёт.

### Safe harbor

Мы не будем преследовать исследователей, которые действуют
добросовестно: тестируют только свои аккаунты/данные, не наносят ущерб
сервису, не нарушают приватность других пользователей и не раскрывают
уязвимость до выпуска исправления.

## Область действия

В scope:

- backend `app/` (FastAPI, JWT, bcrypt, изоляция данных);
- frontend `frontend/` (React, токены в `localStorage`, XSS/CSRF-риски);
- Telegram-бот `bot/` и привязка Telegram-аккаунтов;
- production-конфигурация: Docker Compose, Nginx, сертификаты, скрипты
  деплоя;
- утечки секретов, персональных данных и записей питомцев между
  пользователями.

Вне scope:

- галлюцинации и медицинская некорректность ответов модели — это
  безопасность контента, сообщайте через обычные issues;
- атаки, требующие скомпрометированного сервера или root-доступа;
- социальная инженерия и физический доступ;
- уязвимости сторонних зависимостей без реалистичного сценария
  эксплуатации в VetAssistant (но сообщить всё равно можно).

## Меры безопасности в 1.0.0

- Пароли хранятся только как bcrypt-хэши (`passlib[bcrypt]`, bcrypt < 4.1
  для совместимости).
- JWT подписывается HS256; срок действия по умолчанию — 7 дней; секрет
  задаётся только через `VET_API_JWT_SECRET`.
- Multi-tenancy: `appointments` и `reminders` связаны с `users.id`;
  защищённые эндпоинты фильтруют данные по `user_id` из JWT.
- Telegram-пользователи получают синтетический аккаунт; пароль вычисляется
  через HMAC-SHA256 из Telegram ID и `VET_BOT_AUTH_SECRET`, а не хранится
  в БД.
- Production-стек публикует только `frontend:80/443`; API и PostgreSQL
  доступны только внутри Docker-сети.
- HTTPS через Let's Encrypt, HSTS, редирект HTTP→HTTPS, security-заголовки
  Nginx.
- `.env`, сертификаты и ACME-каталоги исключены из Git.
- CI проверяет `ruff`, `mypy`, `pytest`, frontend-тесты и Docker-сборку.

### Известные ограничения

- Нет rate limiting и CAPTCHA на `/v1/auth/login` — при публичном сервисе
  рекомендуется добавить rate limiting на Nginx/провайдере.
- Нет подтверждения email, восстановления пароля и 2FA.
- JWT хранится в `localStorage`; это осознанный компромисс для SPA.
  Защищайте приложение от XSS и используйте CSP при необходимости.
- История диалога Telegram-бота хранится в памяти процесса и сбрасывается
  при перезапуске.
- Модель может ошибаться; сервис не заменяет ветеринара.

## Обязательный чеклист production-деплоя

Перед публикацией сервиса в интернет:

### Секреты

- [ ] `VET_API_JWT_SECRET` заменён на уникальный случайный секрет:
      `openssl rand -hex 32`. Дефолт `dev-insecure-jwt-secret-change-me`
      использовать **запрещено**.
- [ ] `POSTGRES_PASSWORD` заменён на сильный уникальный пароль (лучше
      hex-строку из `openssl rand -hex 32`); дефолт `vetassistant`
      использовать **запрещено**.
- [ ] `VET_API_ALLOW_PUBLIC_REGISTRATION=false` (публичная регистрация
      закрыта; открывайте только осознанно).
- [ ] `VET_BOT_AUTH_SECRET` сгенерирован отдельно от JWT-секрета, если
      Telegram-бот используется в dev/standalone-режиме.
- [ ] `TELEGRAM_BOT_TOKEN` хранится только в `.env`/менеджере секретов,
      если бот включён.
- [ ] `.env` имеет права `600`, принадлежит сервисному пользователю и не
      попадает в Git.
- [ ] Секреты не выводятся в логи, issue, CI-артефакты и скриншоты.

### Инфраструктура

- [ ] Наружу открыты только `22`, `80`, `443`; API (`8000`) и PostgreSQL
      (`5432`) не опубликованы на хост.
- [ ] Включён HTTPS, работает редирект с HTTP, HSTS и автопродление
      сертификата.
- [ ] DNS A-запись указывает на сервер; сертификат выпущен на правильный
      домен.
- [ ] Настроены бэкапы PostgreSQL и проверено восстановление.
- [ ] Обновления безопасности Ubuntu включены; зависимости регулярно
      обновляются.
- [ ] Логи ограничены по размеру и не содержат секретов/PII.
- [ ] Проверено: запрос без токена к `/v1/appointments` возвращает `401`,
      а пользователь A не видит данные пользователя B.

### Ротация секретов

- Ротация `VET_API_JWT_SECRET` разлогинивает всех пользователей — это
  ожидаемо; выполняйте при подозрении на компрометацию.
- Ротация `VET_BOT_AUTH_SECRET` делает недействительными пароли
  существующих синтетических Telegram-аккаунтов. Планируйте миграцию или
  повторную привязку.
- После смены `POSTGRES_PASSWORD` обновите `VET_API_DATABASE_URL` (или
  переменные, из которых он собирается) и перезапустите `db`/`api`.
- После любого инцидента проверьте логи, смените секреты и отзовите
  скомпрометированные токены/ключи.
